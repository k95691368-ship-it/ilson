# 일손 (ILSON)

**부서의 병목이 도구가 되어 돌아가기까지, 여섯 단계의 실행 기록.**

회사마다 이름이 없어서 아무도 없애 주지 않는 반복업무가 부서마다 쌓여 있다.
재무는 포맷이 서로 다른 채널 정산서를 매주 손으로 붙이고, 운영은 같은 표를
매달 다시 만든다. 이 일들이 사라지지 않는 이유는 기술이 없어서가 아니라
**"부서의 불편 → 합의된 요구 → 동작하는 도구 → 팀 자산"으로 가는 경로가 없어서**다.

일손은 그 경로를 여섯 단계로 만들고, 각 단계에서 **누가 무엇을 결정했는지**를 남긴다.

| # | 단계 | 주인 | 하는 일 |
|---|---|---|---|
| 1 | **신청서** | 현업 부서 | 병목을 적어 낸다 — 신청 부서 / 병목 이유 / 문제 상황 / 바라는 해결 방안 / 지금 걸리는 시간 |
| 2 | **검토** | AX 담당자 | 열람하고 우선순위를 정하고 **수용·반려·보류**를 판정한다 |
| 3 | **협의안** | AX × 부서 | 합의 내용을 문서로 굳히고 **합격 기준**과 **기준선**을 만들기 전에 확정한다 |
| 4 | **제작** | AX 담당자 | 실제로 만든다. 막힌 지점과 해결이 함께 남는다 |
| 5 | **베타 테스트** | 부서 × AX | 실제 담당자가 써 본다. 떨어지면 4단계로 돌아간다 |
| 6 | **성과** | AX 담당자 | 기준선 대비, 차감할 것을 차감한 뒤의 숫자만 적는다 |

---

## 설계에서 특히 신경 쓴 것

**반려 경로가 있다.** 모든 신청을 다 받아 주는 조직은 없다. *"이건 못 만듭니다,
이유는 이것, 대신 이건 해 드릴 수 있습니다"* 를 말하는 화면이 2단계에 있다.
못 만드는 것을 못 만든다고 해야 나머지 약속이 믿긴다.

**기준선을 만들기 전에 잰다.** 6단계에서 *"90분이 3분이 됐다"* 를 말하려면 자동화
**전에** 실제로 재 둬야 한다. 만든 사람이 나중에 회상해서 적은 숫자는 근거가 아니고,
면접에서 "그 90분은 어떻게 아셨어요?"에 답할 수 없다.

**합격 기준을 만들기 전에 정한다.** 3단계에서 무엇을 통과로 볼지 못 박는다.
만든 뒤에 정하면 결과에 맞춰 기준이 움직인다.

**되돌아가는 루프를 숨기지 않는다.** 베타에서 문제가 나오면 4단계로 돌아가고,
그 반복 횟수가 화면에 남는다. 한 번에 통과하는 개발 과정은 없다.

**성과에서 차감한다.** 순절감 = 기준선 × 실행횟수 − 자동 실행시간 −
**사람이 확인하는 시간** − **다시 하는 시간** − **만드는 데 든 공수** −
**운영 비용**. 계산식은 항상 펼쳐져 있고, *"이 숫자를 의심해보세요"* 가
스스로 반박을 던진다.

## 판정과 계산에는 AI가 없다

**이 사이트는 판정·분류·금액 계산에 AI나 외부 API를 호출하지 않는다.** 전부
규칙과 순수 함수가 하고, 그 규칙이 못 정하는 것은 사람에게 올린다. 다만 화면
글꼴과 방문 통계에는 jsDelivr·Google Analytics·Microsoft Clarity를 사용한다.

처음 기획에는 AI가 초안을 쓰는 자리가 여덟 군데 있었다. 만들면서 하나씩
지웠는데, 이유는 같았다 — **초안을 만들어 줘도 사람이 그걸 다시 다 읽어야
한다면 줄어든 일이 없다.** 이 사이트가 다루는 것은 "무엇을 먼저 할지",
"무엇을 반려할지", "이 금액을 성과로 인정할지" 같은 판단이고, 그건 틀렸을 때
책임이 사람에게 돌아온다. 책임이 안 옮겨 가는 자동화는 화면만 늘린다.

그래서 대신 이렇게 했다.

```
┌ 규칙이 정하는 것 ─────┐   ┌ 사람이 정하는 것 ─────┐
│ 어디서 멈춰 있는가     │   │ 무엇을 먼저 할지       │
│ 얼마가 절감됐는가      │   │ 반려할지·보류할지      │
│ 이 숫자를 의심할 근거  │   │ 통과로 볼 기준         │
│ 가 몇 개 남았는가      │   │ (근거와 대안이 남는다) │
└───────────────────────┘   └───────────────────────┘
```

숫자를 내는 자리에는 전부 **반박 규칙**이 붙는다. 표본이 적다, 실행 횟수가
모자란다, 격리된 줄이 안 풀렸다, 계절성을 안 봤다, **부서가 체감과 다르다고
했다** — 하나라도 살아 있으면 그 금액은 '보수적 추정'으로 내려간다.
문장을 지어내는 대신, 믿을 수 없는 이유를 세는 쪽을 택했다.

## 다루는 문제 — 다채널 정산 통합

4단계에서 실제로 푸는 사례다. 서로 포맷이 다른 채널 원장 5종을 하나로 합치고,
결과의 모든 숫자를 원본 엑셀의 시트·행·셀까지 되짚을 수 있게 한다.

| 원본 | 형식 | 이 파일의 난제 |
|---|---|---|
| 자사몰 | CSV UTF-8 | 통화기호 혼재(`₩24,200`), 중복행, 빈 행 |
| 오프라인 채널 | XLSX | 병합셀 + 헤더 4행부터 + **맨 끝 합계행**(적재하면 매출 2배) |
| 오픈마켓 | CSV **CP949** | 인코딩, **반품 음수행** |
| 해외 A | CSV USD | 공개 Settlement Report 필드명 그대로 (**외부 앵커**) |
| 해외 B | XLSX JPY | **다중시트 + 시트마다 다른 헤더 위치**, 기간 밖 데이터 |

같은 제품이 채널마다 다른 코드로 불린다(`NR-CM-100` / `OY1024881` / `87123401` /
`NURIE-CM100-US` / `NR_CM_100_JP`). 별칭 사전 없이는 합산이 불가능하다.

**목표는 선언한 범위 안에서 금액 오차 0원.** 마스터에 없는 코드·합계행·기간 밖
행을 **격리**하는 것은 실패가 아니라 정확한 동작이다 — 모르는 행을 조용히 버리면
합계가 조용히 틀린다. 사람에게 올리는 것이 정답이다.

시험 데이터 설계는 전부 공개한다 → [`docs/시험데이터-설계.md`](docs/시험데이터-설계.md)

## 아키텍처

통합 이력(`/journey`)과 방문자별 체험 공간의 구조, 로컬 실행, 운영 반영 순서는
[`docs/통합이력-개인체험-배포.md`](docs/통합이력-개인체험-배포.md)에 정리했습니다.

```
React 19 + Vite + react-router
        │
        ├─ Cloudflare Pages Functions (functions/api/**)
        │       ├─ _lib/http.js        응답·오류 규격 통일
        │       ├─ _lib/applications.js 신청서 조회·집계
        │       ├─ _lib/signoff.js     합격 기준 서명·이의를 읽는 단 하나의 자리
        │       └─ _lib/rateLimit.js   로그인 없이 여는 화면의 남용 방지
        │
        ├─ shared/**   브라우저와 서버가 같이 쓰는 순수 함수
        │              (판정·금액·반박 규칙이 전부 여기 있다)
        │
        ├─ Supabase (Postgres)  신청서 · 협의 · 제작 · 평가 · 성과
        └─ 브라우저      정산 원본 파일 파싱·병합 (서버 전송 없음)
```

## 실행

```bash
node --version        # v22 LTS (최소 v22.12.0)
npm ci
npm run dev          # 프런트만
npm run dev:demo     # 외부 연결 없는 메모리 PostgreSQL + 실제 API, 5187 포트
npm run dev:full     # Cloudflare Pages Functions + Supabase 연결

npm test             # 전체 테스트
npm run smoke        # 서버 라우트 + 화면 렌더 스모크
npm run lint
npm run build

# 시험 데이터 재생성 (같은 시드 → 같은 출력)
pip install pandas openpyxl
python seed/generate_sources.py
```

운영 DB는 Supabase PostgreSQL이며 Cloudflare Pages는 프런트와 API를 배포합니다.
`SUPABASE_URL`은 `wrangler.toml`, `SUPABASE_SERVICE_ROLE_KEY`는 Pages Production의
암호화된 Secret으로 설정합니다. 프런트 코드나 `VITE_*` 변수에 서버 키를 넣지 않습니다.
운영 설정에는 D1 바인딩이 없으며 Supabase 설정이 불완전하면 연결을 거부합니다.

로컬 API 실행에는 Git에서 제외되는 `.dev.vars`에 개발용 Supabase 연결 정보를
설정합니다. 운영 프로젝트 대신 별도 개발 프로젝트를 사용합니다.
빈 PostgreSQL DB에는 `supabase/migrations/`의 SQL을 파일명 순서대로 적용합니다.
`0000_schema.sql`은 35개 테이블의 빈 스키마이며 사용자 데이터는 포함하지 않습니다.
익명·일반 로그인 역할에는 SQL 실행 RPC 권한을 부여하지 않습니다.

감사 지적 수정본은 `0004_audit_hardening.sql`의 RPC를 사용합니다. 운영 반영 전에는
[감사 지적 수정·반영 절차](docs/audit-hardening-2026-09-13.md)를 확인합니다.
공개 체험에서는 시작 버튼을 누를 때만 별도 공간을 만듭니다. 사내 운영 모드는
서명된 Cloudflare Access JWT와 실제 역할 매핑을 요구하며 이메일 헤더만 신뢰하지 않습니다.

업무 API는 같은 인증 연결의 `GET /api/session`에서 확인한 `scope`를
`X-Ilson-Scope` 헤더로 요구합니다. 모든 보호 조회·쓰기와 체험 초기화 DELETE에
적용되며, 공개 상태 조회·체험 생성·세션 확인은 제외합니다. scope는 인증 토큰이
아니라 사용자가 확인한 계정/공간과 현재 요청의 계정/공간이 같은지 확인하는 조건입니다.
다른 탭에서 계정이 바뀌면 서버는 원래 입력을 새 계정에 저장하지 않고 409
`SESSION_SCOPE_CHANGED`를 반환합니다. 이때 자동으로 다시 저장하지 말고 새 세션과
자료를 확인해야 합니다. 구형 탭이나 직접 API 호출도 세션 확인부터 다시 시작합니다.

이전 중에는 `DB_MAINTENANCE=true`로 새 API 쓰기를 막은 배포를 먼저 적용하고,
백업과 테이블별 건수·내용 대조 후 연결을 전환합니다. 이후 발생한 데이터가 있으므로
오래된 D1 백업으로 단순 복귀하면 안 됩니다. 먼저 새 쓰기를 중지하고 Supabase의
전환 후 변경분을 보존·대조해야 합니다.

## 이 프로젝트가 증명하지 못하는 것

- **실제 부서 회의가 아니다.** 신청서·회의록·이해관계자는 재구성한 시나리오다
- **실사용자 트래픽이 아니다.** 측정 표본은 시드와 자체 로그다
- **대규모 운영 경험이 아니다.** 부서 하나, 도구 하나 규모다

각 항목마다 무엇으로 대체 검증했고 그 대체가 어디까지 유효한지는 앱 안에 적어 둔다.
