# 일손(ILSON) — 기술 설명문

부서가 낸 병목 신청서 한 건이 여덟 단계(신청서 → 검토 → 협의안 → 제작 →
베타테스트 → 사용법서 → 배포 → 성과)를 지나는 동안, **그 과정에서 내려진
모든 결정과 그 근거를 append-only 로그에 남기는** 웹 애플리케이션입니다.

라이브: <https://ilson.pages.dev>

---

## 1. 스택과 배포

| 층 | 선택 | 이유 |
|---|---|---|
| 프런트 | React 19 + Vite, react-router-dom 7 | 번들러 설정 없이 code-splitting. 화면 22개가 라우트 단위 lazy chunk로 분리 |
| 서버 | Cloudflare Pages Functions (Workers 런타임) | 파일 경로 = URL 라우팅. 콜드스타트 없음 |
| DB | Cloudflare D1 (SQLite) | 표 33개. 마이그레이션 SQL로 버전 관리 |
| 오브젝트 | Cloudflare R2 | 부서가 올린 원본 파일 보관 (계보 추적의 뿌리) |
| 테스트 | Vitest | **1,001개** |
| 린트 | oxlint 1.74.0 (버전 고정) | CI에서만 실행 — 아래 §7 |
| CI | GitHub Actions | push마다 린트·테스트·빌드 (~30초) |

배포는 **Git 연동**입니다. `main`에 push하면 Cloudflare가 정적 자산과
Functions를 각각 빌드·배포합니다. 둘은 **배포 시점이 다르므로**, 라이브
검증은 반드시 `content-type`으로 판별합니다 — 자산은 `javascript`, API는
`application/json`. 새 API 라우트가 HTML을 반환하면 그 라우트가 번들에서
누락된 것입니다.

코드 규모: `src` + `shared` + `functions` 합계 약 **31,400 LOC**.

## 2. 아키텍처의 핵심 결정: isomorphic `shared/`

```
shared/**   ← 42개 모듈. 브라우저와 Worker가 같은 파일을 import
   │
   ├─ 브라우저: 입력 검증, 화면 문구 생성, 파이프라인 실행
   └─ Worker  : 동일 함수로 서버 측 재검증, 집계, 응답 조립
```

**클라이언트 검증과 서버 검증이 같은 함수입니다.** 별도 구현이 두 벌
존재하면 반드시 갈라지고, 갈라지는 순간 화면은 "저장됩니다"라고 하는데
서버는 400을 반환합니다. 실제로 이 프로젝트에서 그 사고가 났고
(§6 참조), 그 뒤로 검증 규칙은 예외 없이 `shared/`에 둡니다.

`shared/`에 두는 것과 두지 않는 것의 기준:

- **둔다**: 순수 함수. 입력 → 출력이 결정적이고 I/O가 없는 것.
  판정 규칙, 금액 계산, 문구 생성, 파서.
- **안 둔다**: D1 쿼리, R2 접근, 인증. 이건 `functions/_lib/`.

## 3. 데이터 모델링 제약과 그 우회

**운영 정책상 새 D1 테이블을 만들 수 없는 상태**에서 기능을 계속
추가해야 했습니다. 해법은 `decision_log`를 **확장 지점(extension point)** 으로
쓰는 것입니다.

```sql
CREATE TABLE decision_log (
  id, application_id, stage, actor,
  title, what, why, alternatives,
  unrequested INTEGER,
  link_kind TEXT,   -- ← 레코드의 종류를 나타내는 discriminator
  link_id   TEXT,   -- ← 다른 레코드를 가리키는 느슨한 FK
  created_at
);
```

`link_kind`로 26종의 이벤트를 하나의 테이블에 저장합니다 — 수령확인,
수령거절, 성과확인, 기준서명, 기준이의, 보류해제요청, 같은건손듦,
사용법모름 등. **event-sourcing에 가까운 형태**이고, 그 결과 몇 가지
성질이 따라옵니다.

- **append-only**. UPDATE·DELETE를 하지 않습니다. "취소"는 별도의
  `*취소` 레코드를 추가해 앞의 것을 무효화하는 방식입니다.
- **상태는 리플레이로 계산**합니다. 예를 들어 "지금 이 손듦이 유효한가"는
  시간순으로 훑으며 `같은건손듦` / `같은건아님`을 접어 나가 마지막 상태를
  얻습니다.
- 따라서 **조회 순서가 곧 정확성**입니다. 실제로 여기서 버그가 반복
  발생했습니다 (§6).

`why` 칸은 **설계 취지**(왜 이런 기록을 남기는가)를, `what` 칸은 **그 건에
대해 사람이 적은 말**을 담습니다. 화면에 보여야 하는 것은 후자인데
전자를 읽어서 기능 소개문이 사용자 화면에 뜬 적이 있습니다.

## 4. 파이프라인 — 클라이언트 사이드 결정론적 실행

핵심 기능은 **서로 포맷이 다른 채널 정산서 5종을 하나로 병합**하고,
결과의 모든 숫자를 원본 스프레드시트의 시트·행·셀까지 역추적할 수 있게
하는 것입니다.

```
파일 읽기 → 채널 식별 → 컬럼 매핑 → SKU 정규화 → 값 정제
        → 통화 환산 → 손익 계산 → 검산
```

구현상의 요점:

- **전 과정이 브라우저에서 도는 순수 JS**입니다. 서버는 실행 결과의
  메타데이터(행 수·격리 수·소요 시간)만 기록합니다. 업로드 파일이 서버로
  가지 않으므로 데이터 최소 전송이 성립합니다.
- **인코딩 자동 판별**: CSV를 UTF-8로 디코드해 실패하면 CP949로 재시도.
  판별 확신도(`encodingConfident`)를 함께 반환해 화면이 색을 다르게 칠합니다.
- **XLSX 헤더 오프셋 탐지**: 병합된 제목 행을 건너뛰고 실제 헤더 행을
  찾습니다. 다중 시트에서 시트마다 헤더 위치가 다른 케이스를 처리합니다.
- **채널 식별은 파일명이 아니라 헤더 시그니처**로 합니다. 파일명은 사람이
  바꾸기 때문입니다.
- **격리(quarantine)는 실패가 아니라 정의된 동작**입니다. 합계 행, 미등록
  SKU, 기간 외 데이터, 빈 행, 파싱 불가 값을 버리지 않고 별도 큐로
  분리합니다. "모르는 행을 조용히 버리면 합계가 조용히 틀린다"는 것이
  설계 전제입니다.
- **멱등성**: 동일 파일을 두 번 투입해도 합계가 변하지 않습니다
  (체크섬 기반 중복 감지).

### 정확도 검증

시드 생성기(`seed/generate_sources.py`, pandas·openpyxl, 고정 시드)가
**입력 파일과 정답(ground truth)을 동시에 생성**합니다. 정답 557행 +
격리 정답 75건. 따라서 라벨링 비용이 0이고, `tests/grade.test.js`가
매 실행마다 정답과 대조합니다.

채점기 자체도 검증 대상입니다 — **일부러 틀린 결과를 넣어 채점기가 그것을
잡아내는지**를 테스트합니다. 채점기가 통과시키면 그 테스트가 실패합니다.

## 5. 품질 게이트

배포 경로에 하드 게이트가 걸려 있습니다.

```js
if (lastBeta?.overall !== '통과') blockers.push('베타 테스트를 아직 통과하지 않았습니다.')
if (!manual?.published_at)        blockers.push('사용법서를 아직 확정하지 않았습니다.')
if (blockers.length > 0) return jsonResponse({ error: '아직 넘길 수 없습니다.', blockers }, 400)
```

합격 기준은 `rule` / `human` 두 종류로 나뉘고, `is_required_safety` 플래그가
붙은 기준은 **다른 점수가 아무리 좋아도 차단**입니다. 규칙 기준은 자동
채점되고 근거 문자열(`evidence`)과 어긋난 샘플 행을 함께 남깁니다.

성과 금액에는 **반박 규칙(challenge rules)** 이 붙습니다 — 표본 부족,
실행 횟수 부족, 격리 미해소, 계절성 미확인, 부서 체감 불일치 등.
미해소 반박이 하나라도 있으면 그 금액은 `보수적 추정`으로 강등됩니다.

이 반박들은 **저장되지 않고 읽을 때 계산**됩니다(`buildChallenges`).
`outcome_challenge` 테이블에는 *해소된 것만* 기록됩니다. 이 비대칭이
버그의 원인이 되었습니다 (§6).

## 6. 실제로 발생한 버그와 그 대응

포트폴리오에서 가장 보여드리고 싶은 부분입니다. **버그를 안 냈다가 아니라,
어떤 버그를 어떻게 잡았고 재발을 어떻게 막았는가**입니다.

### `Number(null) === 0`

`Number.isFinite(Number(x))`만으로 유효성을 판단하면 `null`이 0으로
통과합니다. 미채점 항목이 0점으로 2×2 보드 좌하단에 찍혔고, 부서 체감값을
"안 물어봤음"인데 "0분이라고 답함"으로 읽어 반박이 상시 발생했습니다.
**이 프로젝트에서 세 번 발생**했고, 지금은 `value == null || value === ''`
가드를 먼저 둡니다.

### TDZ로 인한 라우트 전체 503

```js
const waitingToStart = items.filter(...)   // items는 이 아래에서 const 선언
```

`/api/overview`가 통째로 503이 되어 **첫 화면이 열리지 않았습니다.**
테스트·린트·빌드 전부 통과했습니다. 문법 오류가 아니라 실행해야만
드러나기 때문입니다.

**대응**: `tests/handlerSmoke.test.js` — D1·R2를 스텁으로 주입해
**모든 라우트 핸들러를 실제로 호출**합니다. GET / POST / DELETE / PATCH /
PUT, 각각 빈 DB와 행이 있는 DB 두 조건으로. 응답 본문에 런타임 에러
시그니처(`before initialization`, `is not a function` 등)가 섞이면 실패입니다.

여기서 한 번 더 배웠습니다 — GET만 보다가 POST를 추가했고, 그때 DELETE를
누락했습니다. DELETE를 채우며 "세어 두지 않으면 또 빠진다"고 주석에 적고
**바로 다음 사이클에 PATCH를 누락**했습니다. 지금은 라우트 파일이
export하는 `onRequest*` 심볼을 화이트리스트와 대조해, **모르는 메서드가
등장하면 테스트가 깨집니다.** 기억에 의존하지 않습니다.

### 존재하지 않는 컬럼

`review` 테이블의 시각 컬럼은 `decided_at`인데 `created_at`으로 쿼리해
라우트가 500. 이 유형을 잡으려고 만들어 둔 `tests/schema.test.js`가
있었는데 **그것도 통과**했습니다 — `alias.column` 형태만 검사하고 있었고,
단일 테이블 쿼리는 별칭을 안 붙이는 게 보통이기 때문입니다.
검사기가 있는데 검사기가 안 보는 자리에 정확히 들어간 사례입니다.
지금은 bare column도 검사합니다.

### `.find()`가 첫 번째를 집는 문제 (append-only 로그의 함정)

부서가 성과 체감을 40분 → 55분으로 정정했는데 서버는 200을 반환하고
값은 40 그대로였습니다. 로그는 시간순으로 오는데 `.find()`가 가장 오래된
레코드를 집었기 때문입니다. **금액 계산이 걸린 버그**입니다 — 그 값으로
'보수적 추정' 강등 여부가 결정됩니다. 같은 패턴을 병합(merge) 조회에서도
발견했습니다(해제 후 다른 건에 재병합 시 옛 대상을 가리킴).

### 저장되지 않는 값을 세는 문제 — 4곳

살아 있는 반박은 계산되고 해소된 것만 저장되는데, `resolved_at IS NULL`로
카운트한 곳이 **네 군데**였습니다. 전부 **조용히 0**이 됩니다 — 예외도
없고 화면도 안 깨집니다.

특히 `/record`(인쇄용 기록)에서 "이 숫자를 의심해보세요" 섹션이 통째로
렌더링되지 않았습니다. 평가자가 출력해 가는 문서에서 **자기 반박이 전부
누락**된 것입니다. `/honesty`(한계를 밝히는 화면)는 자기 반박을 0건이라고
표시하고 있었습니다.

**대응**: `tests/challengeWiring.test.js` — 소스에서
`outcome_challenge` + `resolved_at IS NULL` 조합을 정적 탐지해 실패시킵니다.
반박을 표시하는 라우트가 `buildChallenges`를 호출하지 않아도 실패합니다.

### 화면이 서버 응답의 키를 잘못 아는 문제

```js
const idle = tools?.summary?.idle ?? 0
```

Optional chaining + nullish coalescing 조합은 **키가 사라져도 예외가 없습니다.**
해당 할 일 항목이 영영 표시되지 않을 뿐입니다.

**대응**: `tests/todoWiring.test.js` — `shared/todo.js`에서
`source?.a?.b` 패턴을 정규식으로 추출하고, 대응하는 라우트 핸들러를
**실제로 실행해** 응답 JSON에 그 경로가 존재하는지 검증합니다. 현재 19개
접근 경로를 커버합니다.

### 클라이언트 제어 값이 응답 헤더로

`Content-Type` 헤더에 업로드 시 클라이언트가 보낸 MIME 타입을 검증 없이
넣고 있었습니다. Latin-1 범위 밖 문자(한글·이모지)가 들어가면
`ByteString` 변환 예외로 **다운로드 전체가 500**. 파일은 R2에 멀쩡히
있는데 화면에서만 안 열립니다. 지금은 media type 형태를 검증하고
아니면 `application/octet-stream`으로 폴백합니다.

## 7. 로컬 환경 제약과 CI 이관

개발 머신이 Windows 11 Home이고 **Smart App Control이 활성** 상태입니다.
서명되지 않은 네이티브 바이너리 로드를 차단하므로, oxlint의
`.node` 바이너리가 CodeIntegrity 이벤트 3077/3033으로 블록됩니다.

Smart App Control은 **per-file exclusion을 지원하지 않고**, 비활성화하면
Windows 재설치 전까지 재활성화가 불가능합니다. 되돌릴 수 없는 시스템
설정을 린터 하나 때문에 끄는 것은 트레이드오프가 맞지 않습니다.

→ 린트를 GitHub Actions로 이관했습니다. 부수 효과가 오히려 본질에
가깝습니다 — **검사 결과가 로컬에 머무르지 않고 커밋마다 기록으로
남습니다.** 이 저장소가 주장하는 것이 "기록이 끊기지 않는다"인데 정작
품질 검사만 기록이 없었습니다.

## 8. 테스트 전략

**1,001개 / 46개 파일.** 세 층으로 나뉩니다.

1. **순수 함수 단위 테스트** — `shared/` 42개 모듈. 판정 규칙, 금액 계산,
   파서, 문구 생성.
2. **라우트 스모크 테스트** — 스텁 D1/R2로 전 핸들러를 실제 실행.
   TDZ·오타·undefined 접근 등 실행 시점 오류를 잡습니다.
3. **배선 검증(wiring test)** — 소스를 정적 분석해 "화면이 읽는 키를
   서버가 실제로 주는가", "저장되지 않는 값을 세고 있지 않은가"를
   확인합니다.

3번이 이 프로젝트의 특징입니다. 앞서 나열한 버그의 상당수가
**예외를 던지지 않고 조용히 0/빈 값이 되는 유형**이었기 때문에, 일반적인
단위 테스트로는 잡히지 않습니다.

모든 검사기에는 **"이 검사가 헛돌지 않는가"를 확인하는 테스트**를 함께
둡니다. 정규식이 어긋나 대상을 하나도 찾지 못하면 검사는 통과하지만
아무것도 보지 않은 것이 되기 때문입니다. 실제로 그 상태가 된 적이 있어
추가한 관행입니다.

## 9. 기타 구현 사항

- **인증 없음.** 설계 선택입니다. 현업 부서 담당자에게 계정 생성을
  요구하면 그 시점부터 사용률이 0이 됩니다. 접수번호(0/O, 1/I/L 제외한
  문자셋)를 capability token으로 사용합니다.
- **레이트 리밋**: D1 기반. 실패 시 소비된 한도를 롤백합니다.
- **한국어 조사 처리**: 유니코드 종성 계산(`(code - 0xAC00) % 28`)으로
  은/는·이/가를 선택합니다. 숫자는 읽는 소리로, 영문·기호는 판정 불가로
  두고 `SCM이(가)` 형태로 표기합니다.
- **차트**: 외부 라이브러리 없이 SVG 직접 렌더링.
- **AI 미사용**: 초기 설계에는 LLM 초안 생성 지점이 8곳 있었으나 구현
  과정에서 전부 제거했습니다. 판정·분류·금액 산정은 규칙과 순수 함수가
  수행하고, 규칙이 결정할 수 없는 것은 사람에게 에스컬레이션합니다.
  초안을 생성해도 사람이 전부 재검토해야 한다면 절감된 작업이 없고,
  이 도메인의 판단은 오류 시 책임이 사람에게 귀속되기 때문입니다.
