# 시험 데이터 설계 — 실무 난이도 재현

실제 회사의 채널 정산서는 깨끗하지 않다. 병합셀이 있고, 인코딩이 제각각이고,
맨 끝에 합계행이 붙어 있고, 반품이 음수 행으로 들어온다. **이 파이프라인이
푸는 문제가 바로 그것**이므로, 시험 데이터도 실무와 같은 난이도여야 한다.
깨끗한 CSV 5개를 합치는 것은 아무것도 증명하지 못한다.

이 문서는 그 난이도를 **어떻게 재현했는지**를 전부 공개한다. 읽는 사람이
"이 정도면 실무와 비슷한가"를 스스로 판단할 수 있어야 하기 때문이다.

생성기: [`seed/generate_sources.py`](../seed/generate_sources.py) · 난수 시드 `20260731` 고정 (같은 입력 → 같은 출력)

## 목표: 선언한 범위 안에서는 100%

| 구분 | 목표 | 이유 |
|---|---|---|
| **선언한 범위 안** | **금액 오차 0원, 행 단위 100%** | 다루겠다고 한 것은 완벽하게 처리한다. 타협하지 않는다 |
| **미등록 SKU · 합계행 · 기간 밖 행** | **격리 100% 정확** | 격리는 실패가 아니라 **정확한 동작**이다. 모르는 코드를 조용히 버리면 합계가 조용히 틀린다. 사람에게 올리는 것이 정답이며, 격리해야 할 것을 격리하고 멀쩡한 행을 격리하지 않는 것이 시험 항목이다 |
| **다루지 않는 범위** | 명시적으로 선언 | PDF 정산서, 일자별 변동환율, 부분취소·교환 등. 실패가 아니라 **스코프 선언**이다 ([아래](#여기에-없는-난이도-스코프-선언)) |

## 재현한 실무 난이도 12종

### 1. 컬럼명이 채널마다 전부 다르다
같은 뜻인데 이름이 다르다. 표준 필드로 붙이는 것이 첫 관문이다.

| 표준 필드 | 자사몰 | 올리브영 | 쿠팡 | Amazon US | Qoo10 JP |
|---|---|---|---|---|---|
| 일자 | 주문일자 | 매출일자 | 정산일 | settlement-start-date | 決済日 |
| 상품코드 | 상품코드 | 자체상품코드 | 옵션ID | sku | 商品コード |
| 수량 | 수량 | 판매수량 | 판매수량 | quantity-purchased | 数量 |
| 총매출 | 판매가 | 매출액(VAT포함) | 판매금액 | item-price | 販売金額 |
| 할인 | 할인액 | — | — | item-promotion-discount | — |
| 수수료 | — | 수수료율(비율) | 서비스이용료(금액) | commission | 手数料 |

수수료가 **어디는 비율, 어디는 금액**인 것에 주의. 같은 컬럼명으로 붙이면 틀린다.

### 2. SKU 코드 체계가 채널마다 다르다
같은 제품(`NR-CM-100` 콜라겐 래핑 마스크)이 채널마다 이렇게 불린다.

```
자사몰      NR-CM-100
올리브영    OY1024881
쿠팡        87123401
Amazon US   NURIE-CM100-US
Qoo10 JP    NR_CM_100_JP
```

별칭 사전 없이는 채널 간 합산이 불가능하다. 8개 SKU × 5채널 = 40개 별칭.

### 3. 마스터에 없는 코드 9건 — **버리면 안 되고 격리해야 한다**
채널이 기획세트·묶음상품·한정판을 임의 코드로 올린 상황. 마스터에 매칭이 안 된다.

| 채널 | 코드 | 상품명 |
|---|---|---|
| 올리브영 | OY1099001 | 누리에 마스크 5매 기획세트 |
| 올리브영 | OY1099002 | 누리에 앰플 미니 10ml |
| 쿠팡 | 87199001 | [단독] 누리에 마스크 10매 |
| 쿠팡 | 87199002 | 누리에 선크림 2개 묶음 |
| 쿠팡 | 87199003 | 누리에 토너 리필형 |
| Amazon US | NURIE-BUNDLE-3PC-US | NURIE Trial Kit 3pc |
| Amazon US | NURIE-CM100-2P-US | NURIE Collagen Mask Twin Pack |
| Qoo10 JP | NR_SET_A_JP | ヌリエ トライアルセット |
| Qoo10 JP | NR_CM_100_LTD_JP | ヌリエ マスク 限定版 |

**정답은 "버린다"가 아니라 "검토함으로 격리한다"이다.** 조용히 떨어뜨리면 합계가 조용히 틀린다.

### 4. 인코딩 2종
`03_쿠팡`은 **CP949(EUC-KR)** 로 저장했다. UTF-8로 읽으면 상품명이 전부 깨진다.

```
UTF-8로 읽으면 : ������,�ɼ�ID,�����ǰ��,�Ǹż���...
CP949로 읽으면 : 정산일,옵션ID,노출상품명,판매수량...
```

### 5. 날짜 포맷 4종
| 채널 | 포맷 | 예 |
|---|---|---|
| 자사몰 | `YYYY-MM-DD` | `2026-06-09` |
| 쿠팡 / Qoo10 | `YYYY/MM/DD` | `2026/06/13` |
| Amazon US | `MM/DD/YYYY` | `06/01/2026` |
| 올리브영 | **엑셀 날짜 직렬값** | (셀 타입이 datetime) |

`06/07/2026`이 6월 7일인지 7월 6일인지는 **채널을 알아야 결정된다.**

### 6. 통화 3종 — 환산 없이 더하면 매출이 무의미해진다
`KRW` / `USD`(×1385) / `JPY`(×8.9). 환율은 `master_sku.json`에 고정.

### 7. 병합셀 + 헤더 오프셋 (올리브영)
```
1행  [A1:G1 병합] 2026년 6월 판매 정산 내역서
2행  [A2:G2 병합] 거래처: (주)누리에코스메틱  정산주기: 익월 말일  출력일: 2026-07-05
3행  (빈 행)
4행  매출일자 | 점포 | 자체상품코드 | 상품명 | 판매수량 | 매출액(VAT포함) | 수수료율   ← 진짜 헤더
5행~ 데이터
```
1행을 헤더로 읽으면 컬럼이 전부 `None`이 된다.

### 8. 합계행 함정 (올리브영) — **가장 위험한 항목**
파일 맨 끝에 소계 행이 있다.
```
… | 합  계 | 303 | 6,243,200 |
```
이 한 행을 데이터로 적재하면 **그 채널의 매출이 정확히 두 배**가 된다. 대시보드에서
잡아내기 어렵고(그럴듯한 숫자라서), 회의에서 "왜 올리브영만 이렇게 높죠?"가 나온 뒤에야
발견되는 종류의 오류다.

### 9. 반품 음수행 (쿠팡)
```
2026/06/30,87123407,딥 클렌징 오일,-1,-14600,-1737,-12863
```
전체 행의 약 6%. **부호를 무시하고 절댓값으로 더하면 매출이 부풀려지고**, 반품을 반품으로
인식하지 못하면 반품률 지표가 0이 된다. 정답은 `return_qty`/`return_krw`로 분리 적재.

### 10. 다중시트 + 시트마다 다른 헤더 위치 (Qoo10)
```
2026年04月  헤더 1행   (제목 없음)
2026年05月  헤더 3행   (1행에 병합 제목)
2026年06月  헤더 3행   (1행에 병합 제목)
```
- 첫 시트만 읽으면 6월 데이터를 통째로 놓친다
- 첫 시트로 학습한 헤더 오프셋(1행)을 나머지에 적용하면 **헤더를 데이터로 읽는다**
- **4·5월 시트는 정산 대상 기간(2026-06) 밖**이다. 기간 필터를 걸지 않으면 매출이 부풀려진다 → 정답은 격리(`out_of_period`)

### 11. 중복행 1.2% (자사몰)
결제 시스템 재시도로 실제로 생기는 완전 중복. 멱등 적재(`UNIQUE(source_file_id, source_row_no)`)만으로는
안 잡힌다 — 원본 파일 안에서 이미 두 행이기 때문이다. 내용 기준 중복 판정이 필요하다.

### 12. 값 표기 흔들림 (자사몰)
- 금액: `41100` 과 `"₩24,200"` 이 섞여 있다 (약 35%가 통화기호+천단위 콤마)
- 할인액: `2420` 과 `"7,260"` 이 섞여 있다
- 상품명: 약 8%에 **전각 공백**(`　`)이 섞여 있다 — 한글 입력기에서 실제로 자주 들어온다
- 빈 행: 약 2% (엑셀 → CSV 내보내기의 부산물)

## 여기에 **없는** 난이도 (스코프 선언)

아래는 실제 정산 데이터에는 있지만 이번 범위에서 **다루지 않기로 한 것**이다.
못 푸는 것이 아니라 이번에 손대지 않은 것이며, 이 구분을 앱 화면에도 그대로 적는다.
다루겠다고 선언한 범위 안에서는 오차를 남기지 않는다.

| 다루지 않는 것 | 왜 이번 범위 밖인가 | 넣으려면 |
|---|---|---|
| **일자별 변동 환율** | 여기서는 고정 환율. 검증하려는 것은 "환산을 했는가"이지 "환율이 정확한가"가 아니다 | 정산일 기준 매매기준율 테이블 + `dim_date` 조인 |
| **부분 취소·교환** | 반품은 전량 반품만 재현했다 | 주문 단위 상태 이력이 필요하다 |
| **정산 지연분 소급 반영** | 전월 매출이 이번 달 정산서에 섞이는 상황 | 정산 귀속월과 발생월을 분리한 2축 적재 |
| **VAT 세액 분리** | 올리브영만 "VAT 포함" 표기, 세액을 나누지는 않았다 | 채널별 과세 유형 마스터 |
| **프로모션 분담금** | 채널과 브랜드가 할인을 나눠 부담하는 구조 | 할인 유형별 부담 주체 컬럼 |
| **PDF로만 오는 정산서** | 현실에서 가장 흔한 형태지만 표 추출은 별도 문제다 | 문서 파싱 블록 + 표 구조 복원 |

## 정답셋

`seed/out/ground_truth.json` — 생성기가 원본을 만들면서 **동시에** 뱉는다.
그래서 골든셋을 만드는 라벨링 노동이 0이다.

```
row_count        557   fact로 적재되어야 할 행
quarantine_count  75   격리되어야 할 행 (미등록 별칭 / 합계행 / 기간 밖 / 빈 행)
```

포함 내용:
- `rows` — 원본 행 하나하나가 어떤 fact 행이 되어야 하는지 (파일·시트·행번호까지)
- `quarantine` — 격리되어야 할 행과 그 사유 코드
- `agg_by_channel` / `agg_by_channel_week` — 채널·주차 단위 집계 정답 (행 단위와 별개로 2층 대조)
- `external_anchor_channels` — 자작/외부 분리 보고의 기준
