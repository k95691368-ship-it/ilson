# 통합 이력과 개인 체험 공간

## 범위

- `/journey`: 현재 체험 공간의 신청서 목록.
- `/journey/:id`: 기존 기록 문서의 단계별 근거에 명시적으로 연결한 운영 제품의 사건·실험·판정을 합쳐 시간순 표시.
- 제품 연결 해제는 연결만 제거하며 제품, 사건, 실험은 지우지 않는다. 다시 연결할 수 있다.
- 문제 클러스터를 공유하는 실험은 관련 실험으로 표시하되 그 수치를 특정 신청의 성과에 합산하지 않는다.
- 기존 운영 데이터는 개인 체험에 복사하지 않는다. 가상 신청서 3건으로 시작하고 OverrideLoop를 처음 열면 기존의 고정 시연 시나리오를 해당 공간에만 생성한다.

## 격리와 수명

`DEMO_WORKSPACES=true`인 공개 사이트는 유효한 개인 공간 없이는 업무 데이터 GET/POST 모두 428로 거절한다. `/api/demo/workspace`와 읽기 전용 `/api/health`만 예외다. 앱은 공간 준비가 끝난 뒤 업무 화면을 렌더링한다.

공간 접근 값은 무작위 256비트 토큰이며 HttpOnly, SameSite=Lax, 운영 HTTPS의 Secure 쿠키로만 전달한다. JSON, URL, localStorage에는 저장하지 않는다. 서버 레지스트리에는 SHA-256 해시만 보관한다. 동일 브라우저의 탭들은 하나의 공간을 공유한다. 별도 브라우저 프로필은 별도 공간이다. 로그인 계정 및 조직별 권한 시스템을 대체하는 기능은 아니다.

각 공간은 Supabase PostgreSQL의 비공개 스키마 1개, 업무 테이블 36개를 사용한다. 운영 테이블에서는 구조·제약조건만 복제한다. 외래 키와 자동 증가 시퀀스도 공간 내부에 둔다. 검색 경로에 public 테이블 폴백을 두지 않는다. 기존 SQL 경로는 서버 전용 scoped RPC로 실행하며 공개 역할은 RPC를 실행할 수 없다. 클라이언트 입력을 SQL로 직접 실행하는 엔드포인트는 없다.

유효기간은 생성 후 7일이다. 만료된 공간은 접근을 거절하고, 새 공간 생성 시 최대 8개씩 정리한다. 따라서 만료 즉시 물리 삭제되는 것은 아니다. 레지스트리는 최대 128개로 제한하며 공간 생성·초기화에는 각각 시간당 6회 제한이 있다. 이는 소규모 포트폴리오 체험용 상한이지 대규모 멀티테넌트 운영 설계가 아니다.

초기화는 화면에서 삭제 범위를 확인한 뒤 실행한다. 자신의 스키마만 제거·재생성하고 새 토큰으로 교체한다. 실패하면 DB 트랜잭션이 롤백된다. 늦게 도착한 이전 토큰의 요청은 새 공간을 수정하지 못한다. 다른 공간과 public 운영 데이터는 유지된다. 외부 연동 전송, 외부 AI 호출, 실제 접근 역할 설정은 개인 체험에서 차단한다.

## 로컬 검증

```sh
npm ci
node scripts/dev-demo.mjs
```

`http://127.0.0.1:5187/journey`에서 확인한다. 실제 API 핸들러와 PGlite PostgreSQL을 사용하지만 DB는 메모리에만 있고 종료하면 사라진다. 운영 키를 읽거나 운영 DB를 호출하지 않는다. 서버 측 외부 네트워크 호출도 차단한다. 브라우저 테스트 후 프로세스를 종료한다.

```sh
npx vitest run tests/workspacePostgres.test.js tests/workspaceBoundary.test.js tests/journey.test.js
npm test
npm run lint
npm run build
```

## 운영 반영 순서

2026-09-13 로컬 검증 결과: 테스트 74개 파일·1,350개 통과, 린트·프런트 빌드·Pages Functions 컴파일 통과. 실제 컴파일된 Pages Worker와 메모리 PostgreSQL을 연결해 두 공간 생성, 제품 연결 격리, 자기 공간 초기화, 이전 쿠키 거절, 운영 데이터 보존을 실행했다. 브라우저에서는 목록·상세·제품 연결/해제·초기화 경고/취소를 확인했고 390px 모바일 폭에서 가로 넘침이 없었다. 운영 Supabase 마이그레이션, GitHub 커밋·푸시, Cloudflare 배포는 아직 실행하지 않았다.

Cloudflare Pages의 `next()`는 원래 env 바인딩으로 새 컨텍스트를 만든다. 따라서 미들웨어는 개인 연결을 `context.data.requestEnv`로 전달하고 모든 API 핸들러가 이를 사용한다. env 객체를 방문자별 값으로 공유 변경하지 않는다. 전체 핸들러의 전달 경로와 실제 Pages 방식의 다음 컨텍스트를 회귀 테스트로 검사한다.

2026-09-13 배포 승인 후 확인: 기존 미커밋 디자인·개발환경 변경을 제외한 별도 체크아웃에서 `npm ci`, 빌드, 린트, 테스트 73개 파일·1,347개가 통과했다. 기존 React 테스트의 act 환경 경고는 남아 있으나 실패는 없었다. Supabase의 기존 35개 테이블·62개 행을 CSV로 백업한 뒤 0003을 적용했다. 운영 PostgreSQL의 service_role로 두 공간 생성·변경 격리·초기화·이전 토큰 거절을 실행했고, 익명 RPC 차단·비공개 레지스트리·공간 내부 외래 키·기존 신청 데이터 보존을 확인했다. 해당 검증 트랜잭션은 롤백했다. GitHub 및 Cloudflare 최종 반영 여부는 배포 커밋과 운영 사이트에서 별도 확인한다.

1. 사용자에게 운영 DB 변경과 배포를 승인받는다. 대상 저장소는 `k95691368-ship-it/ilson`, Pages는 `ilson`, Supabase는 `iobeygpmcrmdjhkgtkfg`다. portfolio 프로젝트는 변경하지 않는다.
2. Supabase 백업 및 현재 배포 정보를 보관하고 `0003_journey_workspaces.sql`을 적용한다. 기존 0000~0002가 적용되어 있어야 한다. 이 마이그레이션은 한 번만 적용한다.
3. 서버 전용 역할의 공간 생성·두 공간 간 격리·초기화·익명 RPC 거절을 검증한다. 실제 운영 데이터의 건수와 주요 내용을 반영 전후 대조한다.
4. 요청한 변경만 검토·커밋한다. 기존 미커밋 디자인·패키지·테스트 변경을 무조건 함께 올리지 않는다.
5. `DEMO_WORKSPACES=true`와 새 프런트/API를 함께 배포한다. 이 플래그를 켠 코드를 SQL보다 먼저 배포하면 공간 생성이 실패한다.
6. 서로 다른 브라우저 프로필에서 신청·검토·제품 연결·통합 이력·자기 공간 초기화를 확인한다. 공개 URL에 개인 캐시가 남지 않는지도 확인한다.
7. 오류율과 응답 시간을 15분 관찰한다. 공간 간 노출, 운영 데이터 변경, 생성/초기화 오류는 중단 조건이다.

## 되돌리기

격리 오류가 발견되면 먼저 `DB_MAINTENANCE=true`로 업무 쓰기를 중지한다. `DEMO_WORKSPACES=false`로 단순 전환하면 공개 요청이 기존 공유 운영 데이터 경로로 돌아가므로 격리 문제의 안전한 롤백이 아니다. 수정 배포 전까지 공개 업무 API 접근 자체를 차단하거나 점검 화면을 유지한다. 원인 분석 전에 체험 레지스트리와 데이터를 일괄 삭제하지 않는다. 이전 운영 데이터와 개인 체험 데이터 사이에 자동 병합은 하지 않는다.

향후 업무 스키마 변경 시 기존 체험 스키마에도 마이그레이션을 적용하거나 기존 공간을 명시적으로 만료시키는 계획이 필요하다. public 스키마 변경만으로 기존 개인 공간의 구조가 갱신되지는 않는다.
